## 本次编码修改了什么

- 迁移：仅新增 `V7__victim_profile_facts_and_scenarios.sql`。新增八个基础事实/金额列和 `victim_scenario_profile`，按 PRD 回填三名受害者及九组场景资料。其他既有画像使用明确占位并在缺资料时停用。仅当前画像的故事时间统一为“昨天20:00”。
- 后端：基础字段和三套资料同事务保存；校验三个固定代码恰好各一条、所有资料非空、金额非负且可动用/预留均不大于存款。编辑按场景代码更新子行，保留每套资料身份。启用和启动时均检查资料完整性。
- 接口：管理端双方画像写请求移除 `contextTime`，服务端固定故事时间；当前受害者返回基础事实、三套资料、`profileSchemaVersion=2`。旧快照仍为 v1，新增字段为 null，资料为空列表。
- 前端：复用共同管理页实现基础事实、金额和三页签；故事时间只读；三套未填齐不能保存。配置页详情仅显示当前场景；旧快照显示“未记录”，实际 0 元仍显示 0 元。
- 测试/脚本：新增规则和 MockMvc 测试，补齐组件交互测试；调整现有冒烟脚本的写请求字段和表清单，避免契约变更使调用方失效。
- 未修改：V1～V6、旧 Prompt、会话快照写入结构、资金流水/扣款、新结果码、报告规则和 Qwen。原有 README、四份文档、OpenAPI 修改及 `project-QianYe/` 保留，不纳入本阶段代码提交。

## 你需要重点检查什么

1. 管理端三套表单的中文内容和九组初始资料是否符合你的业务表达，尤其核实习惯、行动边界与停止条件。
2. 三个页签切换后输入是否保留；漏填第三套时是否出现对应错误。
3. 负金额、可动用/预留超过存款是否有清楚反馈；故事时间是否固定且不可编辑。
4. 配置页切换场景时是否只展示该场景资料，旧历史是否显示“未记录”而不是 0 元。
5. 页面长文本、窄屏和表单布局是否符合预期。
