# AI反诈情景推演平台 V1.2 分阶段开发计划

> **面向执行者：** 本计划按阶段顺序执行，每个阶段结束后必须停止编码，向用户提交「本次编码修改了什么 / 需要重点检查什么 / 测试证据」，等待用户确认后才能进入下一阶段。禁止在一个回合内跨阶段连续修改。阶段内任务使用复选框（`- [ ]`）跟踪。

**Goal（目标）：** 把现有 V1.1（9 张表、旧四类结果、报告 v1、CosyVoice）增量升级到 V1.2：受害者基础事实＋三套场景资料、本场资金与逐笔流水、三类正式结果与提前终止、报告 v1/v2、历史颜色/滚动框和 Qwen 语音；旧记录保持只读兼容。

**Architecture（架构）：** 沿用 Spring Boot 模块化单体 + Vue 3。数据库新增 `victim_scenario_profile`、`simulation_fund_flow`，并在会话/轮次上增加资金摘要；资金流水是权威，会话/轮次摘要同事务汇总。结果判定从“候选结局”改为 `DEFRAUDED / IDENTIFIED / LIMIT_REACHED`，旧码只读；报告按 `content_schema_version` 同时支持 v1/v2；Qwen 只替换 TTS 适配层，不改变 SSE、存储和发布顺序。

**Tech Stack：** Java 21（Corretto 21）、Spring Boot 3.5.16、MySQL 8.0.45、Flyway；Vue 3.5.44、Vue Router 4.5.1、Pinia 3.0.3、Vite 6.4.4、TypeScript 5.9.3、Vitest 5.0.5。不新增依赖。

## 一、执行规则（每个阶段必须遵守）

1. **严格按阶段顺序执行。** 阶段 N 未获得用户确认，不得开始阶段 N+1，即使阶段 N 的代码已经能编译。
2. **分支只创建一次。** 阶段 0 首次从当前基线创建 `feature/v1.2`，后续阶段沿用同一分支；不每阶段从 `main` 重新开分支。阶段内可本地提交，不 push。
3. **每阶段结束必须提交四类证据：**
   - 修改文件清单；
   - 执行的测试命令与真实结果；
   - 手工检查步骤与结果（含 SQL/HTTP/UI 证据）；
   - 已知限制与未覆盖项。
4. **每个阶段有独立可运行结果。** 不允许“先改一半、下阶段再补齐”导致当前阶段无法启动或旧功能不可用。
5. **旧数据只读兼容。** 不批量重写旧快照、旧报告、旧结果；旧记录缺少新字段时按 null/`fundsRecorded=false` 表达，不能补 0 冒充真实值。
6. **不改已执行迁移。** 只能追加 V7 及之后的迁移；不修改 V1～V6，不使用 `flyway repair` 绕过校验。
7. **不新增 HTTP 操作/SSE 事件。** 仍为 44 项操作、11 类事件；如需改变契约，先停下更新四份文档与 `openapi.yaml`，不得在代码里先斩后奏。
8. **不新增依赖。** 不使用 Lombok、MapStruct、新图表库、新状态库；前端沿用现有内联 SVG/CSS。
9. **测试从简。** 每个阶段只写与改动直接相关的关键测试，完成后做简单功能测试与人工检查；不默认执行 90 场、18 种全组合、大规模并发或反复压测。
10. **日志与隐私边界不变。** 不记录完整对话、报告正文、Prompt 渲染结果、内部心理、凭据或密钥；`internal_note` 不进入任何用户响应/SSE。
11. **金额一律整数元。** 不做小数、不做浮点累计；前端只展示，不自行计算余额/亏损并写回。
12. **金额守恒。** 付款不超当前余额；不凭空补钱；返款只来自实际到账；预留释放必须有理由且累计不超过本场冻结的预留总额；实际亏损 = max(0, 累计支付 − 累计返款)；只有当前轮实际执行的动作可入账。
13. **返款规则。** 只有 `TASK_REBATE`/`FAKE_INVESTMENT` 允许实际返款，每场累计实际返款≤300 且≤累计实际支付；单笔返款累计≤其关联原付款；`IMPERSONATION_LOAN` 无实际返款。Scammer 的 `claimedRefundYuan` 只是声称金额，不写流水、不增加余额；有实际返款时必须非空且≥实际返款合计，声称可以大于实际。
14. **故事时间固定“昨天20:00”。** 新画像/新快照由服务端写入；管理端不再接收 `contextTime`；旧快照保留旧文案。
15. **三套场景资料必须齐全。** `TASK_REBATE`、`FAKE_INVESTMENT`、`IMPERSONATION_LOAN` 各一条；缺一条不能启用/保存。
16. **旧结果名不冒充新结果。** 旧 `NOT_DEFRAUDED` 仍显示“未受骗结束”，不得显示“已识破”；旧 `UNDETERMINED` 仍显示“结局未定”。

## 三、复审重点（Review Focus）

以下是 V1.2 最容易在真实使用中出问题、且常规任务测试容易漏掉的五类情况。**每条都必须在对应阶段的任务测试中出现：**

1. **旧记录被新代码“补值”或改名**——升级后打开 V1.1 的演绎/报告，旧快照没有三套资料、旧报告只有五字段、旧结果是 `NOT_DEFRAUDED`。合理预期：页面不报错、不显示 0 元余额、不把“未受骗结束”改名为“已识破”，旧失败报告重试仍按 v1。测试落在阶段 2（历史读取）、阶段 4（结果展示）、阶段 5（报告 v1/v2）、阶段 6（历史 UI）。
2. **资金被凭空创造或透支**——模型给出超过余额的付款、同一条消息重复付款、返款没有实际到账、预留释放超额或无理由、跨轮重复提及旧付款、声称大额返款却按声称入账。合理预期：资金动作在消息**保存前**校验；超余额/非法金额退回对应角色重生，错误台词不保存；重复回执不重复计数；返款只增加余额；亏损下限 0；首笔不计追加；预留累计释放不超过冻结的预留总额；刷单/投资实际返款≤300 且≤累计支付，借款无返款；声称只是文本/内部校验字段，不写流水。测试落在阶段 3、阶段 4。
3. **结果优先级错误**——同轮目标达成后又停止、超限时已有受骗、超限时未受骗、提前终止被写成正式结果；把“余额==0”直接当资金不足。合理预期：目标/已受骗停止 → `DEFRAUDED`；无受骗且停止 → `IDENTIFIED`；完整轮超限已有受骗 → `DEFRAUDED+limitReason`；无受骗未识破 → `LIMIT_REACHED+limitReason`；半轮到时仍 `INTERRUPTED/TIME_LIMIT`；资金不足按可用余额＋可释放预留判断，零余额有预留不终止、非零余额不足要终止；资金不足/角色退出不生成报告。测试落在阶段 4。
4. **报告 v1/v2 混用**——新会话用 v2 结构、旧会话用 v1；旧失败报告重试被错误升级 v2；v2 字数/节点/建议/资金摘要不合格仍保存成功。合理预期：按 `report_content_schema_version` 分流；旧报告只读；v2 校验失败可重试；成功报告不被覆盖。测试落在阶段 5。
5. **画像三套资料与“当前场景”混淆**——普通详情展示了三套全部、显示了“重点易受骗”标签、后台只保存两套、金额超过初始存款。合理预期：普通详情只展示当前场景；后台三套齐全才能启用；不展示教学标签；`availableFundsYuan`/`reservedFundsYuan` 均不大于 `initialSavingsYuan`。测试落在阶段 1、阶段 6。

### 3.1 范围

**做：**
- 新增资金实体/仓库/纯规则；**Victim 输出付款/预留释放，Scammer 输出实际返款**；两类动作分别在各自消息保存前校验，保存时同一事务写流水并更新轮次/会话摘要。
- 校验：金额>0、付款≤余额、预留释放≤预留总额、返款只增余额、重复动作不重复计数、首笔不计追加。刷单/投资累计实际返款≤300，且≤累计实际支付；单笔返款累计≤关联原付款；借款无实际返款。

**校验与生成流程：**
